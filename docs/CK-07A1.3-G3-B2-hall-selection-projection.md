## Commands and identity

```text
/ck hall select <hall-code> <program-uuid> <stage-uuid>
/ck hall retry <hall-code>
```

Commands resolve one registered Hall by case-insensitive code, authenticated
server player UUID, and the player's current `WorldIdentity` UUID. They do not
accept a client-supplied player identity. Unknown/foreign-world/non-owned Halls
are rejected before HTTP. Python additionally checks Hall and Program ownership
on PUT. Moving to another world while the request is pending prevents physical
commit in the old world. Native physical access also checks its world UUID.

Retry is an authoritative GET followed by Stage/Graph read and physical
projection. It never repeats PUT, rolls selection back, invokes Stage rebuild,
ensures a child, or saves shared domain content.

## Transport and DTO

`HallSelectionApiClient` uses the existing Graph shared-secret header/environment
and API base URL. GET calls `/api/v1/halls/{hall_id}/selection?player_uuid={uuid}`.
PUT sends exactly player UUID, target Program/Stage UUIDs and the GET's
`expected_selection_revision`. B1 permits header-free selection requests with
shared-secret authentication, owner checks and CAS; this client uses that mode.

`HallSelectionParser` requires the Program envelope version `ck-program-v1`,
selection version `ck-hall-selection-v1`, `status:ok`, complete canonical UUIDs,
the exact requested Hall/world UUIDs, a nonnegative signed-bigint revision,
`content_scope:SHARED_PROGRAM` and `projection_state:DESIRED_ONLY`. PUT additionally
requires a boolean `changed`. Structured backend errors preserve their HTTP
status/error code; protocol and availability failures remain distinct transport
results. The selection response has a dedicated parser and does not use the G1
context echo contract. `TransportContextParser` itself is unchanged.

PUT responses must match the requested Program/Stage. A no-op preserves revision
and WorkingCopy; a real change advances revision by exactly one. A Stage change
inside the same Program preserves WorkingCopy; a Program change must supply a
different WorkingCopy. Returning to P after Q is a fresh identity. Invalid
handoffs stop before Stage/Graph HTTP or world writes.

GET may advance the known revision but cannot decrease it or change the known
selection at the same revision. Known desired state from a failed attempt is
retained as the next attempt's revision floor. Persisted selected Stage identity
is retained separately from temporary legacy enter/back navigation, so those
local transitions do not manufacture backend selection changes.

## State and lifecycle

The registered `Hall` continues to describe the physically committed display.
`HallSelectionState` separately holds the desired selection and attempt:

```text
DISPLAYED → SELECTION_REQUESTED → DESIRED_COMMITTED
          → PROJECTION_PREPARING → DISPLAYED
                                 ↘ PROJECTION_FAILED
```

Editing and SAVE are disabled from request start, including uncertain HTTP
failure. This conservative state is recovered with retry. After a successful
PUT but failed projection, backend desired state remains committed and the
registered displayed identity remains unchanged. The player receives the
specific failure and retry command. Successful physical commit alone updates
displayed Program/WorkingCopy/Stage identity and selection revision.

An attempt captures source context/Stage, world UUID, known selection/revision,
Hall generation, navigation generation, Program-status generation and source
Graph slot lifecycle. Beginning an attempt renews Hall generation and advances
navigation/status generations. This invalidates old CRUD/SAVE/status/reconnect/
bootstrap completions. Accepting a validated desired selection removes only
that Hall's old Graph slots, invalidating pending Graph/Wire token authority.

Target reconciliation is keyed by the desired Hall/Program/WorkingCopy/Stage.
The existing Stage-switch token keeps the source physical identity while its
validated pending selection supplies the target projection context. Every bind,
prepare, queued commit and terminal cleanup checks ownership of that attempt.
Cleanup removes only the lifecycle owned by the failed attempt; it cannot erase
a newer selection or reinstall. A stale PUT cannot start Stage GET; stale Stage
GET cannot start Graph reconciliation. Stale Graph/render/completion callbacks
cannot write the world, SAVE sign, or initiate a status refresh.

## Physical path

`HallSelectionCoordinator` performs backend selection transport/handoff, then
delegates to `StageNavigationCoordinator.projectSelection`. The existing
`StageProjectionAssembler` and `StageSwitchProjection` perform all target
assembly, collision planning, application and rollback. There is no parallel
Stage navigation/domain engine.

Selection requires B1's physical Stage metadata. Hall/world/origin/size must
match the target Hall and logical layout, and Graph Hall/world/origin/size,
Stage epoch/revision, snapshot format and catalog must agree. Physical Program
positions use that validated B1 origin; blocks, Graph/Wire layout and routes
remain Stage-relative in the domain.

The full side-effect-free planner checks source/target Hall bounds, Program block
types/orientations/unique positions, complete Wire geometry, target collisions
and the planned space after removing managed CK cells. Foreign blocks are never
cleared. It snapshots affected physical state before any mutation and rechecks
world state, world UUID, target slot lifecycle and navigation authority immediately
before writes, including after the final physical read.

Under the existing synchronized Stage-switch commit boundary, application is:

1. Clear managed CK cells in the source/target projection volumes.
2. Place target Program blocks.
3. Apply the preflighted Wire plan.
4. Render authoritative aggregate dirty/SAVE state from the Stage response.
5. Commit the new displayed registry identity and revision.

Preflight/stale failures perform zero writes. An application exception rolls back
affected physical states and the previous SAVE display, keeps the old displayed
identity, and leaves backend desired selection intact for retry. Rollback still
depends on the world adapter successfully restoring state; real runtime failures
require Minecraft acceptance rather than inference from an in-memory backend.

No extra post-selection status GET is launched: the authoritative Stage response
already carries aggregate dirty state. Existing Program-status and Wire
completion paths remain fenced and are disabled while selection is unresolved.

## Regression evidence and acceptance boundary

The tests run the production selection coordinator, Stage navigation, registry,
Graph projection store, Wire coordinator/completion and physical planner/commit.
Test doubles replace only transport and Minecraft physical access. A local HTTP
server additionally exercises the real selection client and parser.

Coverage includes DTO/auth/CAS errors, revision/identity contradictions, persisted
vs temporary Stage identity, delayed PUT/Stage/Graph replies, queued commit,
delete/reinstall, superseding navigation generation, pending Wire completion,
P→Q→P, same-key reconciliation, wrong/moving worlds, late final-read lifecycle
change, invalid geometry/origin/bounds, foreign collisions/preservation,
application rollback, failure/retry and two-Hall physical/identity isolation.
The two-Hall test projects the same Program/Stage in different coordinates with
different WorkingCopies, then changes Hall A while asserting Hall B's display,
content and projection remain intact. Unit evidence is not Minecraft runtime
acceptance.
