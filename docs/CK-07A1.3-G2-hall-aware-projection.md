## ProjectionKey

Immutable Kotlin data class:

ProjectionKey(hallId: UUID, programId: UUID, workingCopyId: UUID, stageId: UUID).

A kulcsot az interakcióval azonosított Hall hiteles transport-contextjéből és a
kért Stage ID-ból képezzük. Stage ID önmagában sem store lookuphoz, sem request
tokenhez nem fogadható el. Nincs első egyező Hall szerinti kontextusfeloldás.
A Graph snapshot továbbra is közös Python Stage-domainadat; az esetleges legacy
Hall-mezőjét nem használjuk a fizikai célterület kiválasztására.

## Store-ok és lifecycle

| Állapot / token | Kulcs és fencing |
|---|---|
| GraphProjectionStore slot | Teljes ProjectionKey |
| GraphRequestToken | ProjectionKey, monoton lifecycle generation, request generation |
| StageGraphView | ProjectionKey, epoch, revision, lifecycle generation |
| WireInteractionCoordinator worldStates | ProjectionKey → lifecycle generation + world status |
| WireStageContext | Teljes mount-context, Stage, fizikai origin/size, epoch, lifecycle generation |
| StageUpdateFence | Hall, mountkulcs, Stage, Hall generation, projection generation, navigation generation, epoch/revision |
| StageSwitchToken | Hall/mount-context, Hall generation, navigation/status generation és source Stage |

A store-on belüli lifecycle-számláló monoton nő. Új slot, epochváltás,
authoritative reconciliation és CRUD-invalidáció új generációt kap.
Eltávolítás után az azonos kulccsal létrehozott slot más generációjú:
a régi token sem apply, sem fail művelettel nem módosíthatja.

Hall install/mountcsere az adott Hall összes slotját eltávolítja, új Hall
generációt kap és saját root/active slotot hoz létre. Más Hall slotját nem érinti.
Törölt Hall generációját tombstone-ként megőrizzük, így régi, fence nélküli
reconnect-lista nem telepítheti vissza. Új, hiteles install külön belépési pont.

Wire render előtt a coordinator újraellenőrzi a lifecycle-t és a registry
fizikai projection fence-ét. Régi parancs bizonytalan eredménye után a transport
adapter csak még élő lifecycle esetén indíthat helyreállító GET-et.
Az elavult worldStates bejegyzések nem olvashatók SYNCED-ként új lifecycle-ban.

## HallRegistry és navigáció

A Stage ID alapján Hallt választó hallForStage és stageUpdateFence segédfüggvény
megszűnt. A graph/saveDirty olvasók Hall ID-t várnak; isActiveStage teljes
ProjectionKey-t és epochot vár. A fizikai hallAt feloldás csak egyetlen találatot
fogad el.

A navigáció target slotja az indító Hall/mount saját target Stage-kulcsára jön
létre. A prepare külön reconciliation lifecycle-t indít. Commit előtt a
navigation generation és a target projection lifecycle is ellenőrzött.
Sikeres váltás csak ugyanazon Hall source slotját távolítja el.
Meghiúsult váltás a saját, már nem aktív pending target slotját érvényteleníti.

## Világvetítés

- A Hallnak, mountnak és aktív Stage-nek egyeznie kell a WireStageContexttel.
- A slot lifecycle-jának is aktuálisnak kell lennie.
- A Wire origin/size pontosan a registryben nyilvántartott Stage fizikai
  origin/size értékeivel egyezik.
- A Stage pozitív méretű és a Hall belsejében marad; a blokkok a Stage-en belül
  vannak. A felső koordináták ellenőrzése Long aritmetikával történik.
- Hall DTO install és Stage-response alkalmazás előtt megtörténik a bounds check.
- Stage switch előtt mind a source, mind a target fizikai területe és a wire
  cellák relatív tartománya ellenőrzött; a fizikai committer a target snapshotot
  és lifecycle-t is ellenőrzi.
- A Wire projector teljes snapshot preflightja továbbra is megelőzi a
  világírásokat. Eltávolításkor a world-access által visszaadott pozíciókat is
  Stage-határra szűri, ezért másik Hall wire-ja nem távolítható el.
- A WorldRenderer Stage-blokkvetítése külön is ellenőrzi a Hall-határokat.

## Reconnect és SAVE board

A G1 Hallonkénti transportja megmaradt. A reconnect az adott Hall saját slotját
reseteli, utána annak Graph/Wire állapotát kéri le és vetíti ki. A befejező
SAVE-board callback az új reload után rögzített teljes fence-et ellenőrzi.
Mountcsere, reinstall, Stage-váltás, új epoch/revision vagy újabb status kérés
esetén a régi callback nem frissíthet táblát.

Sikertelen Graph reconciliation után a tábla nem igazolhat tiszta állapotot.
A Program dirty/status továbbra is a teljes közös Program állapotát jelzi.
A SAVE a teljes közös Programot menti; két projection slot nem két tartalmi
workspace. A másik Hall friss authoritative GET-je jogosan mutathatja a közös
Program új tartalmát.

A Stage CRUD/SAVE DTO legacy hall_id mezője nem a transport-context:
a G1 HTTP-válaszvalidáció ellenőrzi az indító mountot, a registry a captured
fence Halljának koordinátarendszerébe képezi a relatív blokkadatokat.

## Két-Hallos Minecraft acceptance

Kizárólag külön jóváhagyással, eldobható tesztvilágban és tesztadatbázissal:

1. Ugyanazt a Programot mountold két, egymástól távoli Hallba, eltérő WorkingCopy
   ID-val. Ellenőrizd a Hallonként eltérő fejléceket és a teljes ProjectionKey-ket.
2. Mindkettőn root Stage: A-ban Wire place, B-ben Graph refresh. Késleltesd és
   fordított sorrendben engedd át a válaszokat. Csak a saját fizikai területük
   változhat; egyik callback sem tüntetheti el a másik Hall wire-ját.
3. A root → child → grandchild → child → root útvonalán B maradjon rooton.
   A régi A Graph/Wire válaszokat minden lépés után engedd át; B változatlan marad.
4. Indíts SAVE-et A-ban, majd válts Stage-et vagy telepítsd újra A slotját.
   A késői válasz ne frissítsen táblát. B saját authoritative status GET-je a
   közös Program mentett/dirty állapotát mutassa.
5. Reconnect: Hallonként külön Graph GET, külön slot és fizikai vetítés.
   A blokkok után Wire/Graph, végül a megfelelő Hall SAVE-táblája frissüljön.
6. Késleltetett válasz mellett töröld és telepítsd újra ugyanazt a slotkulcsot;
   a régi callback nulla blokkírást okozzon.
7. Teszt mountcsere/hibás WorkingCopy után ellenőrizd a régi callbackek
   elutasítását. Azonos identity melletti újratelepítést is vizsgáld.
8. A közös Programban módosíts A-ból, majd B-ben végezz authoritative refresh-t:
   az új közös tartalom megjelenése elvárt, nem izolációs hiba.

## Kockázatok és értékelés

Minecraft acceptance még nem futott. A Python mount-validáció továbbra is
request-entry preflight, nem tranzakciós mount-lease. A Fabric a már megismert
helyi mount/lifecycle változásokra fence-el; külső DB-változást a Python
HTTP-validációja és a következő authoritative refresh tár fel.

A stale callbackek tudatosan kiesnek; a friss megjelenítéshez új authoritative
refresh/reconciliation szükséges. Hall-tombstone és utolsó Wire status
metaadatok a szerverfolyamat élettartamáig megmaradhatnak.

Értékelés: CONDITIONAL GO. A G2 implementáció és az automatizált teszt/build kapu
elkészült. A külön Minecraft acceptance még szükséges a runtime elfogadáshoz.
A G2 után megállunk; commit és deploy csak külön jóváhagyással történhet.
