## Formátum és korreláció

Mindkét komponens `CK_DIAG` prefixű, egysoros JSON-rekordokat ír. Induláskor
`DIAGNOSTICS_READY`, illetve `PY_DIAGNOSTICS_READY` jelzi a `ck-diag2-v1` sémát.
A Python-rekordok PID-t is tartalmaznak; ez különválasztja a WH restart két oldalát.

A Graph, Program és általános Fabric HTTP-kliens kérésenként UUID-t küld az
`X-BlockCommander-Diagnostic-Id` fejlécben. Ez kizárólag korreláció: nem identity,
nem CAS-verzió, nem domain `request_id`, és nem jogosultsági adat. A WH ugyanazt
az ID-t naplózza; régi kliens fejléc nélküli kéréséhez saját diagnosztikai ID-t ad.
A domain Graph-parancs `request_id`-ja külön is megjelenik.

A Graph GET begin/HTTP/result/complete rekordjai ugyanazt a diagnosztikai ID-t
használják. A store-alkalmazást a Hall–Program–WorkingCopy–Stage key és a
request/lifecycle generation köti hozzá. SAVE/státusz callbackeknél a key,
epoch/revision és státusz-/navigation-/Hall-generation az összekötő adat.

A Python belépési rekord identityje még kérésből származik
(`context_verified:false`); a sikeres meglévő transport-validáció után az
események a feloldott identityt és `context_verified:true` értéket kapják.
Ehhez nincs második repository-resolve vagy workspace-betöltés.

Nincs secret/header-dump, teljes request/response body, blokkfelirat, Graph-,
Wire- vagy Route-tartalom. A SAVE receipt csak Stage-ID/verzió/changed adatokat
tartalmaz. A diagnosztikai sink hibája elnyelődik; a domain eredmény változatlan.

## Kiértékelés

- `WIRE_LOCAL_REJECT` és nincs hozzá `WIRE_COMMAND_SEND`/POST HTTP: helyi sync gate.
  Előtte lehetett Graph GET; ez nem CKW-törési mutation.
- Fabric POST indul, de ugyanazon diagnostic ID-hoz nincs Python receive:
  transport/proxy/megérkezési probléma; ellenőrizd a Fabric HTTP-eredményt.
- Python HTTP receive után nincs command receive, de van hibaválasz:
  auth/context/parser gate. A strukturált hibakód megmondja, melyik.
- `PY_GRAPH_VERSION_CHECK` → `PY_GRAPH_REJECT`: Python verzióellenőrzés;
  a kérés és az aktuális workspace értékei ugyanabban a rekordban szerepelnek.
- Python Graph GET 200 → store `EPOCH_CONFLICT`: Fabric epoch-fogadási gate;
  nézd a megelőző reconnect reasont és a requested/current/response Stage-ID-kat.
- SAVE receipt + `dirty_after:false`, majd státuszbegin és elutasított apply,
  végül dirty táblarender: a kijelzési/státuszláncot kell vizsgálni. Egy későbbi,
  valódi domainmódosítás jogosan is újra dirtyvé teheti a Programot.
- BUG-01 és BUG-02 közös okát csak korrelált eseménysor alapján állítsd.

## Kockázatok és telepítési ajánlás

Az INFO-szintű naplózás többlet I/O-t és időzítési változást okoz, registry/store/
Program-lock alatt is. Csak műveleti határokon naplóz, nem cellánként; nincs
payload- vagy secret-dump. A UUID-k és koordináták miatt a logok továbbra is
üzemeltetési adatok. A logger hibájának elnyelése szándékos: ilyenkor hiányozhat
diagnosztika, de nem változhat a művelet eredménye.

A `SAVE_SIGN_RENDERED` szerveroldali írást jelez, nem kliensoldali render-ACK-t.
Stage-switch közben a renderer Hall-argumentuma a commit előtti source Stage-et
tartalmazhatja (`stage_role:RENDER_ARGUMENT`); a közvetlenül előtte álló
`SAVE_SIGN_TARGET` azonosítja a cél-Stage-et és a normál/rollback szerepet.

**A jelenlegi teljes bundle közvetlen production telepítésére NO-GO.** A forrás
B1+B2-t is tartalmaz, a futó rendszer G1/009. Előbb külön jóváhagyott,
alapverzióhoz illesztett instrumentációs rollout vagy a B1+B2 teljes rolloutjának
külön felülvizsgálata szükséges. A DIAG2 nem oldja fel a korábbi bugok NO-GO-ját.
