# CK-07/A1.3-G3/B1 — Authoritative Hall Selection & Mount

Backend implementation based on clean `main` at `a06cc02`. G2/R1 Fabric
implementation/tests remain unchanged. No commit, deployment, production
migration or Minecraft world mutation is part of this slice.

## Persistence and transaction

`010_hall_selection.sql` adds `active_stage_id uuid NOT NULL` and
`selection_revision bigint NOT NULL DEFAULT 0 CHECK (selection_revision >= 0)`
to `hall_program_mounts`. Existing mounts start at their Program root, revision
zero. The existing Hall primary key guarantees one mount per Hall; Program ID
remains nonunique. A composite FK `(program_id, active_stage_id)` uses the existing
Stage composite unique key and restricts deletion. The existing composite
WorkingCopy FK remains; a new unique constraint on mounted WorkingCopy IDs
prevents simultaneous identity sharing across Halls. Historical unmounted
WorkingCopies remain available. Inconsistent existing data makes migration fail
atomically; it is never repaired by silently selecting a different Stage.

PUT locks the Hall and its mount, verifies current Stage/WorkingCopy consistency,
Hall owner, target Program owner and persisted Stage membership, then compares
revision. Program and target Stage rows receive share locks during validation.
Allocation and mount update commit together. No Stage/Graph content is written,
no SAVE runs, and no workspace is loaded by the selection operation.

## HTTP contract

Both endpoints require the existing `X-BlockCommander-Graph-Secret` transport
authentication. The player UUID is the server-asserted player identity, as in
existing APIs; shared-secret possession alone does not bypass ownership checks.

`GET /api/v1/halls/{hall_id}/selection?player_uuid={uuid}` requires the Hall owner.

`PUT /api/v1/halls/{hall_id}/selection` accepts exactly:

```json
{
  "player_uuid": "<UUID>",
  "program_id": "<target UUID>",
  "stage_id": "<persisted target UUID>",
  "expected_selection_revision": 0
}
```

PUT requires the player to own both Hall and target Program. Revision must be
a nonnegative signed-bigint integer (booleans are rejected). Unknown/missing
fields and invalid UUIDs are rejected using the existing Program API diagnostics.
The client cannot supply world coordinates or override the Hall's world UUID.

Both return HTTP 200 with this envelope; only PUT includes `changed`:

```json
{
  "api_version": "ck-program-v1",
  "selection_api_version": "ck-hall-selection-v1",
  "status": "ok",
  "changed": true,
  "selection": {
    "hall_id": "<UUID>",
    "world_uuid": "<actual Hall world UUID>",
    "program_id": "<UUID>",
    "working_copy_id": "<UUID>",
    "active_stage_id": "<UUID>",
    "selection_revision": 1,
    "content_scope": "SHARED_PROGRAM",
    "projection_state": "DESIRED_ONLY"
  }
}
```

This is a dedicated identity-handoff contract. It deliberately has no G1
`transport_context` echo: a successful Program change returns a NEW triple.
All three existing G1 headers may optionally assert the OLD mount, checked in
the same transaction as CAS. Partial/malformed headers remain errors; stale
or foreign old identity produces `CONTEXT_MISMATCH`. Header-free selection is
authenticated and guarded by owner checks plus revision. Existing Graph/Stage/
Program endpoints keep the unchanged G1 context-validation rules.

| HTTP | Selection error code | Meaning |
| --- | --- | --- |
| 403 | `FORBIDDEN` | Hall or target Program owner mismatch |
| 404 | `HALL_NOT_FOUND` / `MOUNT_NOT_FOUND` / `PROGRAM_NOT_FOUND` | Missing target |
| 422 | `STAGE_NOT_PERSISTED` | Missing or workspace-only Stage; no implicit SAVE |
| 409 | `STAGE_PROGRAM_MISMATCH` | Persisted Stage belongs to another Program |
| 409 | `SELECTION_CONFLICT` | Expected revision is stale |
| 409 | `CONTEXT_MISMATCH` | Optional old mount assertion differs |
| 409 | `INVALID_SELECTION` | Invalid persisted Stage/WorkingCopy reference |
| 503 | `REPOSITORY_ERROR` | Transaction/storage failure, including allocation |

Errors use `status:error`, `error_code`, `message` and `diagnostics`, following
the existing Program envelope. Authentication and DTO syntax errors keep the
existing transport/Program codes.

## CAS and WorkingCopy lifecycle

CAS is strict, including no-op requests. Same revision + same Program/Stage
returns `changed:false`, unchanged revision and unchanged WorkingCopy. Every
actual selection change increments revision once. A stale request always gets
409, even if its requested selection currently matches: GET supplies the current
identity/revision so the client can distinguish an already fulfilled request
from another selection. This avoids concealing root→child→root ABA changes.
Two actual PUTs with the same expected revision have exactly one winner.

Stage changes inside a Program keep WorkingCopy ID. Program changes allocate a
fresh UUID, including P→Q→P. A UUID allocation/INSERT failure rolls the entire
transaction back. WorkingCopy remains identity metadata for shared content.

## Reads, coordinates and workspace cache

`ensure_stage` selects the persisted active Stage; initial aggregate creation
uses root only if no mount exists. An existing broken mount never creates a new
Program/root. `load_stage_for_hall` also selects `active_stage_id`.

World Hall lists, authenticated Hall detail (`GET /halls/{id}`), rebuild/restore
and reconnect DTOs include active Stage/revision and its content. Player Hall
lists expose selection metadata. Mounted Program reads include the full current
selection in `mount`; Program `mounts` include active Stage/revision.
Each enriched Hall response captures one selection identity before loading its
Stage, so an intervening PUT cannot pair another selection's Stage with it.

`hall_projection.project_stage` builds response-only coordinates from the selected
Hall's min coordinates plus the shared Stage's logical `origin_rel_*`. It sets
Hall/world/origin/size, and recomputes absolute legacy block coordinates from
their relative positions. Context-scoped Program Stage and Graph `state` DTOs
use the same projection. `domain_layout`, relative blocks, Graph nodes, Wire
cells and route steps stay unchanged. No legacy `stages.hall_id` coordinates
are copied from Hall A into Hall B's DTO; shared headers/snapshots are untouched.
Physical-fit checking still belongs to the existing Fabric bounds guard.

Program DTO reads call `refresh_mounts` under the existing Program lock. This
read-through operation replaces only `ProgramWorkspace.mounts`, after successful
repository loading. It never replaces headers, Stage workspaces, snapshots,
epochs, revisions or dirty flags. A failed metadata read leaves old cache
contents intact and the next read retries. PUT does not depend on cache refresh,
so a committed selection cannot be reported as a failed write because cache
refresh failed. Other cached Programs retain their dirty workspaces across
mount changes; their mount lists refresh on their next DTO read.

## Verification and B2 boundary

The unit suite covers strict DTO parsing, response-only coordinate projection,
and cache refresh/retry with workspace identity, epoch, snapshot and dirty
preservation. The guarded real PostgreSQL suite covers migration upgrade from
009, FK/CHECK/unique enforcement, shared mounts, child selection and restart,
different physical/world origins, relative Graph/Wire equivalence, restore,
owner/membership failures, transient Stage rejection, Program ABA, strict
idempotence, concurrent actual PUTs, UUID allocation rollback, corrupt selection
without fallback, deleted Hall and metadata-cache failure.

Only the identity-verified disposable B2-T PostgreSQL target is used. The runner
checks Docker/container/volume/network identity and the database marker and role
before destructive tests. Production configuration/DB/world is not used.

B2 must implement the explicit selection handoff, selection-revision fencing,
the current-player-world restriction and the physical projection state machine.
A committed desired selection is not proof of a successful Minecraft projection.
Existing Fabric bounds/origin checks stay enabled. It must handle failed physical
projection/retry without allowing edits through an obsolete identity. Backend
selection does not push live cross-Hall updates. Reads continue to expose the
shared live Python workspace, including unsaved content with its dirty state.
